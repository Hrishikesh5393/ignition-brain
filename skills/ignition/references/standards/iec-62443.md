# IEC 62443 OT Security

**Standard:** IEC 62443 (formerly ISA-99) — security for **Industrial Automation and Control
Systems (IACS)**. It is a family:

| Part | Scope |
|------|-------|
| 62443-1-1 | Terminology, concepts, models (zones, conduits, SL, FR) |
| 62443-2-1 | Security program for the **asset owner** |
| 62443-2-4 | Security program requirements for **service providers / integrators** |
| 62443-3-2 | **Risk assessment & system design** — partitioning into zones and conduits |
| 62443-3-3 | **System security requirements & security levels** — the SRs, grouped by FR, per SL |
| 62443-4-1 | Secure **product development** lifecycle |
| 62443-4-2 | Technical security requirements for **components** (the CRs) |

This doc is the **global / universal** layer — the *why / what standard*. The Ignition-mechanism
detail and this site's role/zone mapping live in
[`skill/references/standards/security-roles.md`](./security-roles.md),
the project gateway profile, and
the project naming convention.

## Zones and conduits (62443-3-2)

- **Zone** — a grouping of assets that share the same security requirements and trust level.
- **Conduit** — a defined communication path between zones; all cross-zone traffic goes through
  a conduit with explicit, enforced controls (firewall, protocol break, authentication).
- **Rule:** no implicit cross-zone communication. Every flow is a named conduit or it doesn't
  exist.

## Reference architecture levels (Purdue model, 62443-1-1 / ISA-95 aligned)

| Level | Contents | Typical zone |
|-------|----------|--------------|
| 0 | Process — sensors, actuators, drives | Process / cell zone |
| 1 | Basic control — PLC, RTU, protection relays | Control zone |
| 2 | Area supervisory — **HMI, SCADA, the Ignition gateway (edge/area)** | Supervisory zone |
| 3 | Site operations — historian, MES, **central Ignition gateway**, reporting | Operations zone |
| 3.5 | **Industrial DMZ (IDMZ)** — replicated historian, patch/AV servers, remote-access broker, reverse proxy | DMZ zone |
| 4 | Enterprise business network — ERP, business IT | Enterprise zone |

The Ignition gateway typically sits at Level 2 or 3. Its northbound links (to enterprise BI, an
external IdP, a cloud MQTT broker) cross the IDMZ; its southbound links (OPC-UA/PLC drivers,
gateway network to edge gateways) stay in OT. Each of those is a conduit.

## Security Levels (SL 1–4, 62443-3-3)

| SL | Protects against |
|----|------------------|
| **SL 1** | Casual or coincidental violation |
| **SL 2** | Intentional violation using *simple* means, low resources, generic skills, low motivation |
| **SL 3** | Intentional violation using *sophisticated* means, moderate resources, IACS-specific skills, moderate motivation |
| **SL 4** | Intentional violation using sophisticated means, *extended* resources, IACS-specific skills, high motivation |

SL-T (target) is assigned per zone during risk assessment; SL-C (capability) is what a product
can deliver; SL-A (achieved) is what the deployed system actually has. The gap is the work.

## Foundational Requirements (FR 1–7) and how they land on an Ignition gateway

| FR | Name | Representative SRs | On the Ignition gateway |
|----|------|--------------------|-------------------------|
| **FR 1** | Identification & Authentication Control | SR 1.1 (human auth), SR 1.2 (device/process auth), SR 1.5 (authenticator mgmt), SR 1.7 (password strength), SR 1.8–1.9 (PKI / public-key), SR 1.11 (failed-login lockout), SR 1.13 (auth over untrusted networks) | Named **user source** / external **IdP** (SAML/OIDC) — no shared logins; MFA at the IdP; service identities are distinct named accounts; API keys are credentials, scoped and rotated |
| **FR 2** | Use Control | SR 2.1 (authorization enforcement), SR 2.4 (mobile code), SR 2.8–2.10 (auditable events, storage, audit failure handling) | **Roles → security levels/zones** mapped to resource permissions; least privilege; project/designer/gateway-config access gated; audit profile enabled |
| **FR 3** | System Integrity | SR 3.1 (communication integrity), SR 3.2 (malicious code), SR 3.4 (software/info integrity), SR 3.8 (session integrity) | **TLS** on the gateway web server and gateway network; signed/verified modules; restrict Designer & gateway-network trust; config-change control via a reviewed authored → verify workflow |
| **FR 4** | Data Confidentiality | SR 4.1 (info confidentiality at rest/in transit), SR 4.3 (use of cryptography) | TLS everywhere; secrets not in plaintext resources; encrypted `.gwbk` handling; DB connections over TLS |
| **FR 5** | Restricted Data Flow | SR 5.1 (network segmentation), SR 5.2 (zone boundary protection), SR 5.3 (general-purpose comms restriction) | Gateway placed in the correct Purdue level; only required ports open; gateway-network conduits explicit; no direct L4↔L1 path |
| **FR 6** | Timely Response to Events | SR 6.1 (audit log accessibility), SR 6.2 (continuous monitoring) | Audit log to a durable store, forwarded to SIEM; gateway logs monitored; alarm on security events |
| **FR 7** | Resource Availability | SR 7.1 (DoS protection), SR 7.3 (control system backup), SR 7.4 (recovery & reconstitution), SR 7.6 (network/security config settings) | Scheduled **gateway backups** stored off-box; redundancy where SL-T requires; documented restore procedure; hardened config baseline |

*unverified:* exact Ignition setting names (user-source types, audit-profile options,
API-key/token model) differ by Ignition version and edition — confirm against a live gateway
read or [`security-roles.md`](./security-roles.md) before citing one in a resource or script.

## When this applies

> **Every task that touches gateway configuration, authentication, roles/permissions, the
> gateway network, external connections, credentials, API keys, audit logging, or backups.**
> Also any resource or script that *reads or writes* a secret, connects outbound, or changes
> who can do what. Not every tag-typing or view-layout task invokes 62443 directly — but the
> standing credential rules below apply to **all** agent work, always.

---

## agent rules

> - **Never hardcode a credential** — password, API key, token, DB string, private key,
>   bearer token — in a project resource, a tag, a script, a named query, or a commit. Use the
>   gateway's secret/credential mechanism and reference it. If you find one hardcoded, report it
>   as a finding; don't propagate it.
> - **Never widen an API key's / service account's scope to make a call succeed.** If a call
>   needs more scope, that is an escalation to the supervisor, not a self-service change. Least
>   privilege (FR 2 / SR 2.1) is the default.
> - **Treat the gateway config as OT.** Config changes go through the authored →
>   flush+fsync → `requestScan()` → runtime-verify workflow, never ad-hoc edits; assume changes
>   are audited and attributable.
> - **TLS is not optional** (FR 3 / FR 4). Don't disable cert verification, don't add an
>   `http://` connection where `https://` is available, don't downgrade the gateway web server.
> - **One named identity per human and per service.** No shared accounts, no "admin/admin", no
>   reusing a person's login for a script. Service accounts get their own scoped role.
> - **Don't turn off the audit profile or reduce its retention** to quiet a log.
> - **Don't open a gateway-network conduit or a firewall port** to route around a problem —
>   surface it. Cross-zone flow is a design decision (FR 5).
> - **Back up before a risky change**; know the restore path (FR 7 / SR 7.3–7.4).
> - Security *choices* (which roles, which zones, which IdP, retention periods) come from
>   the project gateway profile and
>   [`security-roles.md`](./security-roles.md) — read them, don't invent.

## Smells

| Smell | FR breached |
|-------|-------------|
| Credential string literal in a script, tag value, or named query | FR 1 / FR 4 |
| One `admin` account used by people and scripts alike | FR 1 / FR 2 |
| API key with gateway-wide scope used for one narrow read | FR 2 (SR 2.1) |
| `http://` connection or `verifySsl=false` where TLS is available | FR 3 / FR 4 |
| Gateway reachable from the enterprise/Level-4 network with no DMZ | FR 5 (SR 5.1–5.2) |
| Audit profile disabled, or pointed at a volatile store | FR 6 (SR 6.1) |
| No scheduled off-box `.gwbk`; no documented restore | FR 7 (SR 7.3–7.4) |
| Designer / gateway-network trust left wide open ("allow all") | FR 3 / FR 5 |
