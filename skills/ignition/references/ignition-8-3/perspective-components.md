# Ignition 8.3 — Perspective component reference

Compact developer reference built from the live docs.inductiveautomation.com 8.3 manual: 72 component pages plus the Event Types, Style, and resource.json reference pages.

## How Perspective components work

**Property categories.** Every component (and every view) exposes its properties grouped into categories in the Designer's Property Editor:

- **Props** — the component-specific configuration and runtime data (what this reference documents per component below). Fully described only on each component's own doc page.
- **Position** — where the component sits inside its parent container. The available position properties depend entirely on the parent container type (e.g. Coordinate gives x/y/width/height/rotate; Flex gives grow/shrink/basis/display; Column gives span/rowIndex/colIndex/order; Breakpoint gives size). See each container's Props block above for its Child Component Position properties.
- **Meta** — properties the Perspective module itself defines for every component: `name`, `visible`, `tooltip` (enabled/width/text/style/delay/sustain/location/tail), `contextMenu` (enabled/items/style, with item types submenu/link/method/message/separator), and the hidden-by-default `domId` and `tabIndex`.
- **Custom** — a free area for user-created properties (Value, Object, or Array) that scripts and bindings can read/write; the recommended place for user-created properties since Props/Position/Meta can contain hidden backend properties a same-named custom property could collide with.
- **Params** — only present on Views (and the Embedded View / docked-view / page mechanisms that pass values into them). Params are declared `input`, `output`, or `in/out`; input params are the view's public "arguments," output params are read-only from outside the view, and in/out params are bindable on both sides of the boundary.

**Property data types**: value (boolean/numeric/string), object, array, plus the special-cased `Dataset`, `Date`, and `Color` value variants that get dedicated editors in the Property Editor. Properties can be **Persistent** (saved with the project/view; the default) or **Transient** (not saved — bound properties default to transient since their value is about to be overwritten anyway). Properties can also be access-restricted to **Public** (default), **Protected** (server ignores browser writes), **Private** (also hidden from browser reads), or **System** (read-only, not user-removable) — useful for stopping a user from tampering with a component via browser dev tools.

**Bindings.** Most Props (and many Meta/Style properties) can be bound. Perspective's binding types are: Property, Tag, Tag History, Expression, Expression Structure, Query, HTTP, and MongoDB. Tag and Property bindings can be made **bidirectional** (writes flow back to the source), and a bidirectional binding can enable **Coalesce** to combine rapid child-property writes into a single writeback. A property with a binding is non-persistent by default.

**Style vs. classes.** Every component has a `style` property (and often several sub-object `style` properties for its internal parts — header, rows, track, etc.) built from the categories in the Style Reference (Text, Background, Margin/Padding, Border, Shape, Misc). A **Style Class** groups a set of style settings under a name in the project's Styles folder, and multiple classes can be applied to one component (later-alphabetical class wins on conflicts; inline `style` always wins over any class). Style Classes support **bindings**, **animation** (duration/direction/iterations/timing/delay/fillMode + keyframe stops), and **Element States** (e.g. hover) — see "Styles" below.

**Containers** (the root container types, chosen once per view and unchangeable afterward):
- **Coordinate** — free x/y/width/height placement, in fixed pixels or percent-of-parent (`mode`); the default for new views. Best for pixel-precise or SCADA-mimic layouts.
- **Flex** — CSS-flexbox-style layout (`direction`, `wrap`, `justify`, `alignItems`, `alignContent`); children get grow/shrink/basis. Best for responsive rows/columns that reflow.
- **Breakpoint** — a single width (or height) breakpoint splitting content into exactly two named zones (`size` position property); good for a simple mobile/desktop split.
- **Column** — a 12-column responsive grid (Bootstrap-like), with per-breakpoint span/order/rowIndex/colIndex. Best for dashboard-style responsive grids.
- **Tab** — a set of tabs (classic or other menu styles) each holding its own child content; good for organizing many views of a screen behind navigation.
- **Split** — two children separated by a user-draggable divider (`orientation`, `split.position`); good for resizable master/detail panes.

**Events and scripts on components.** Right-click a component → **Configure Events** to attach one or more **Actions** to an **Event** (component, system, mouse, keyboard, touch, wheel, pointer, focus, selection, text-composition — full catalog in the Event Types Reference below). Actions run top-to-bottom but **not synchronously** — a slow action does not block a faster one queued after it. Action types include Navigation, Popup, Dock, Script, Theme, Alter Logging, Refresh, Request Print, Fullscreen, Workstation Mode, Login/Logout, Authentication Challenge, and mobile-app-only actions (Accelerometer, Scan Barcode, Scan Ndef NFC). A **Script Action** gets a built-in `event` object describing the trigger. Separately, many components also expose **Component Events** (e.g. Table, Tree, Map, Accordion, Form, File Upload) that behave like Vision extension functions and are scriptable from the Component menu bar/Property Editor — those are called out per-component below where documented on a component's own page.

**Where components live in a view's JSON.** Every Ignition project resource (including a view) is stored as a `resource.json` file plus data files it manifests (commonly `data.bin` or `config.json`, which for a view holds its root container, its property tree — props/position/meta/params/custom — and the nested tree of child components). `resource.json` itself carries **Scope** (Gateway/Client/All), **Version** (parser version for that resource type), **Restricted**/**Overrideable** flags, the **Files** manifest, and **Attributes** (auto-tracked `lastModification`/`lastModificationSignature` plus any user attributes). A project's `project.json` similarly stores the project's title, parent (for inheritance), description, and enabled state.

## Event types

From the Perspective Event Types Reference. `event.<property>` is available inside a Script Action for the matching class.

| Class | Representative events | Key `event.*` properties |
|---|---|---|
| Component Events | Varies per component (e.g. `onActionPerformed`, `onFileReceived`, `onCellEdit`) — see each component's Props/Events above | Component-specific |
| System Events | `onStartup`, `onShutdown` (view or component mount/unmount, incl. session logout/timeout) | none special |
| Mouse Events | `onClick`, `onContextMenu`, `onDoubleClick`, `onMouseDown/Up/Enter/Leave/Move/Over/Out` | `altKey`, `ctrlKey`, `shiftKey`, `metaKey`, `button`, `buttons`, `clientX/Y`, `pageX/Y`, `screenX/Y`, `relatedTarget`, `getModifierState()` |
| Pointer Events | `onPointerOver/Enter/Out/Leave/Up/Down/Cancel/Move` (touch + stylus) | `pointerId`, `pointerType`, `isPrimary`, `pressure`, `tangentialPressure`, `tiltX/Y`, `twist`, `width`, `height` |
| Keyboard Events | `onKeyDown`, `onKeyUp`, `onKeyPress` (deprecated, use onKeyDown) | `key`, `keyCode` (deprecated), `charCode` (deprecated), `location`, `repeat`, `altKey/ctrlKey/shiftKey/metaKey`, `getModifierState()` |
| Text Composition Events | `onCompositionStart/Update/End` (IME / voice-to-text input) | none special |
| Focus Events | `onFocus`, `onBlur` | none special |
| Selection Events | `onSelect` (text selection) | none special |
| Touch Events | `onTouchStart/Move/End/Cancel` | `altKey/ctrlKey/shiftKey/metaKey` |
| Wheel Events | `onWheel` | `deltaX`, `deltaY`, `deltaZ`, `deltaMode` (0=px,1=line,2=page) |

An **Action Performed** event (`onActionPerformed`) is available on most interactive Input components (Date Time Input/Picker, Barcode Scanner Input, Button, Checkbox, Dropdown, Multi-State Button, Numeric Entry Field, One-Shot Button, Radio Group, Slider, Toggle Switch) — fired on the component's primary interaction (click, check, select, etc.), regardless of the component's `enabled` state, so gate side effects in the script rather than relying on the event not firing.

## Styles

- Style properties are grouped into six menus, all CSS-based: **Text** (font family/size/color/weight/italic/line-height/letter & word spacing, alignment, transform, decoration, shadow, overflow-wrap/text-overflow), **Background** (color, image, position, clip/repeat/attachment/size, box-shadow), **Margin and Padding** (per-side), **Border** (style/width/color/radius per side, plus outline), **Shape** (fill/stroke/stroke-width for SVG-based components), and **Misc** (opacity, cursor, overflow/overflow-x/overflow-y).
- **Style Classes** live in the project's Styles folder, can be nested in folders, and are applied via a component's `style.classes` property; the `ia_` name prefix is reserved for Perspective's built-in styling. Multiple classes apply in alphabetical order (last wins on conflicting properties); an inline `style` value always overrides any class. Classes support **bindings**, **animation**, and **Element States** (style overrides for e.g. `:hover`), plus **Media Query** conditions.
- An **Advanced Stylesheet** (`stylesheet.css`, opt-in per project) lets you write raw CSS; target a Style Class with the `.psc-<name>` prefix and a built-in Perspective/CSS class with `.ia`.
- **Theme variables**: built-in themes are `light`, `dark`, and derived `light-warm`, `light-cool`, `dark-warm`, `dark-cool` (session-selected via `session.props.theme`). Themes expose CSS custom properties such as `--neutral-10` … `--neutral-100` and `--seq-1` … `--seq-5` (sequential palette); reference them directly as the variable name on a component's style property, or wrapped in `var(--seq-4)` inside a Style Class/stylesheet. Only `light`/`dark` are locked system resources — override them by creating an `overrides-light`/`overrides-dark` theme resource that `@import`s the original and adds `:root { --var: value; }`; the `-warm`/`-cool` derived themes can be edited directly (but revert on upgrade).

## Gotchas and 8.3 notes

- **XY Chart is a new 8.3 component** that replaces an older, now-deprecated XY Chart. Its bullet `radius` property replaces the old bullet `width`/`height` properties; if migrating a project, consult the archived deprecated-component docs for the old property names.
- **Power Chart Tag History `drv` syntax carries forward**: any `drv` key-value pair syntax used for the SQL Tag Historian provider in Ignition 8.1 Power Chart configs will still work unchanged in 8.3.
- **Alarm Journal Table / Alarm Status Table responsive mode** disables or removes some table features (certain column/paging interactions) once `responsive.enabled` triggers card-based rows — test alarm screens at your target breakpoint before relying on every column feature.
- **Table component events aren't in a "Component Events" section.** Unlike Button/Motor/Form, the Table's cell-edit and other component-level events are referenced from inline prop descriptions and the linked Table Scripting page rather than a distinct `## Component Events` block — check the Table Scripting page directly rather than assuming there are none.
- **Form is the newest, most structurally different Input component** — it nests Columns → Rows → Widgets rather than a flat Props list, and it fires both a component-scoped `onSubmitActionPerformed`/`onCancelActionPerformed` pair *and* an independent Gateway-scoped "Form Submission" event/handler, which is easy to conflate.
- **File Upload's actual receive path is a Component Event** (`onFileReceived`), not a prop binding — files must be picked up with a script action on that event, typically to move the upload to the Gateway or another destination.
- **View Object is not a palette component.** Its doc page documents the root View's own Props/Position/Meta/Params (same for every container type) — don't expect to drag it from a palette; it's referenced from Views in Perspective for the shared view-level property list.
- **Report Viewer requires the Reporting Module** to be installed on the Gateway; without it the component renders but has nothing to display.
- **Root container type is locked in at view creation** — Coordinate, Flex, Breakpoint, Column, Tab, and Split each drive a different Position property set on children, and switching container types later isn't supported; a new view (or nested container) is required instead.
- **Bound properties default to non-persistent**, which can cause a visible "flash" to an empty/default state on load (classically seen on Embedded View's `path`) — set the property Persistent explicitly and give it an initial value if that flash matters.
- **Custom properties belong in Custom or Params, not Props/Position/Meta.** Those three categories can contain hidden, backend-only properties; a user-created property with a colliding name can produce unintended behavior. Custom and Params have no such hidden properties.
- **Property access levels (Public/Protected/Private/System)** only block *browser-side* JavaScript reads/writes (e.g. via dev tools) — they do not restrict bindings or Python scripts running server-side, and Style Class *names* remain visible/interactable from the browser regardless of access level.
- **Dataset numeric precision**: JS doubles only safely represent integers up to 2^53−1; a Long/Double column value beyond that (e.g. via a bound Dataset tag) can silently change value when read back through the Perspective front end.
- **Multiple Style Classes apply in alphabetical order** (not declaration order) — a class later in the alphabet overrides an earlier one on conflicting properties, and any inline `style` value on the component always wins over every class.
