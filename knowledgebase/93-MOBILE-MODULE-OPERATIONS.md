# Ignition 8.3 Mobile Operations: Deployment, Performance & Support

## 1. Mobile App Installation & Updates

There is no binary to version-bump and push through an app store review cycle in the typical Ignition mobile deployment — see the companion doc (92-MOBILE-MODULE-PERSPECTIVE.md) for why "the app" is almost always a browser tab, a PWA, or a thin WebView wrapper pointed at a Gateway URL. That changes how "installation" and "updates" work in practice:

- **Web/PWA path (the common case)**: "Installing" is the end user visiting the Gateway URL once and tapping "Add to Home Screen." "Updating" happens automatically — the next time the PWA opens, the service worker checks the Gateway for a newer compiled Perspective bundle and swaps it in, typically on the *next* launch rather than mid-session (the currently open session keeps running the old bundle until closed/reopened, to avoid yanking components out from under an operator mid-task). There is no per-device update rollout to manage; a Designer publish is the update.
- **WebView wrapper path**: if a client has a genuine `.apk`/`.ipa` wrapper, the wrapper binary itself rarely needs updating (it's just a WebView shell) — only the URL it points to changes when Gateway content changes, which again happens automatically on next load. The wrapper binary only needs a new build/redistribution if the wrapper's *native* chrome changes (icon, splash screen, permissions manifest) or the OS forces a WebView engine deprecation.
- **Cache-busting gotcha**: because service workers cache aggressively by design, a Designer publish that changes a view sometimes doesn't show up on a phone that has the PWA already installed, because the cached bundle is still considered valid. The fix is ensuring the Perspective project's cache/version identifier increments on publish (Ignition manages this automatically per-project in normal operation) — if a client reports "I published but my phone still shows the old screen," the first troubleshooting step is a hard-refresh/force-close-reopen of the PWA before assuming a real deployment bug.
- **First-open onboarding**: because there's no store listing, there's no built-in "what's new" changelog UX; if that matters to the client, it has to be built as an in-app "release notes" popup gated on a version-number tag/prop comparison.

## 2. Device Enrollment & Management

Mobile devices touching an Ignition Gateway generally fall into two management models, and picking the wrong one for the deployment is a common early-project mistake:

- **BYOD (bring your own device)**: no MDM, no enrollment — users just navigate to a URL and log in with their Ignition/IdP credentials. Lowest cost, fastest rollout, but zero device-level control: no way to remotely wipe a lost phone's cached session, no enforced OS/browser version, no restriction on which networks the device can also touch. Appropriate for lower-risk, read-mostly dashboards (a supervisor checking KPIs from their personal phone).
- **Corporate-managed (MDM-enrolled)**: devices enrolled in Intune, Jamf, Workspace ONE, or SOTI MobiControl. This is the appropriate model for any deployment that writes to process data, handles PII, or runs on a shared/pooled device fleet (warehouse handhelds, wall-mounted kiosks). MDM buys you: forced device passcode/biometric, remote wipe, app/URL allowlisting (locking the device to only the Ignition Gateway origin, blocking general web browsing), and enforced OS patch levels — all things that are otherwise unenforceable from the Ignition side, since Ignition has no visibility into device posture over plain HTTPS.
- **Kiosk mode**: Android Enterprise "dedicated device" / "single-app kiosk" profiles or Apple Configurator "Single App Mode" lock a device permanently into one Chrome/Safari tab pointed at the Gateway, with hardware buttons disabled. This is the standard pattern for wall-mounted operator tablets — it removes the "user navigated away and now the tablet is stuck on a lock screen" support call almost entirely.
- **Certificate-based device auth (advanced)**: for higher-security environments, MDM can push a client certificate to enrolled devices and the Gateway's web server/reverse proxy can require mutual TLS, so only enrolled devices can even reach the login page — unenrolled devices get a TLS handshake failure before ever seeing Ignition's login form. This is a reverse-proxy/network-layer control, not an Ignition Gateway setting.

Gotcha: enrollment decisions need to be made *before* a pilot, not retrofitted — moving a fleet of already-BYOD-provisioned phones into MDM enrollment after go-live is a real IT project (user consent, device re-provisioning) and frequently gets deprioritized once the pilot "just works," leaving a permanent security gap.

## 3. Performance Optimization for Mobile

Mobile CPUs, GPUs, and memory budgets are a fraction of a desktop client's, and Perspective's rendering is JavaScript/DOM-based, so bloated views that run fine on an engineer's workstation can visibly lag or crash-reload on a mid-range Android device.

- **Component count matters more than it seems**: every Perspective component is a DOM subtree with its own binding subscriptions. A dashboard with 200+ components (common in "port the whole Vision screen over" migrations) can produce a noticeably janky scroll/render on mobile even though it's smooth on desktop. Prefer fewer, denser components (a single templated Table over 40 individually-placed Label/Value pairs) for any view that must run on mobile.
- **Binding count and polling rate**: each polling binding is a periodic subscription; dozens of 1-second polling bindings on one mobile view compounds CPU/battery drain fast. Where possible, prefer tag-change/event-driven bindings over polling, and lengthen polling rates for non-critical mobile dashboards (a KPI tile refreshing every 10s is usually fine where a 1s desktop trend pen is not needed).
- **Image/asset weight**: background images, icon sets, and especially embedded SVGs with complex paths are common silent offenders — a 4K background PNG that's invisible-cost on desktop broadband can meaningfully delay first paint on a cellular connection. Serve appropriately sized/optimized images (WebP where supported) rather than relying on CSS to scale down a huge source file.
- **Chart/trend complexity**: high-density trend pens (multiple pens, long time ranges, high sample rates) are CPU-expensive to render and re-render; on mobile, favor coarser aggregation (use Tag History's built-in aggregation modes rather than pulling raw high-rate data) and fewer simultaneous pens per view.
- **Animation/transition restraint**: CSS transitions and Perspective's built-in animation properties are cheap individually but compound on lower-powered GPUs; heavy use of animated Popup transitions, continuously-animated gauges, or auto-scrolling marquees on a mobile page is a common source of reported "the app feels slow on my phone" tickets that don't reproduce on desktop QA.
- **Test on mid-range hardware, not the newest iPhone**: a huge share of industrial BYOD/company fleets are 2-3 year old mid-range Android devices, not the latest flagship. Performance testing exclusively on a new iPhone or a development laptop's Chrome DevTools mobile emulation reliably misses real-world lag — see Section 10.

## 4. Network Efficiency (Bandwidth, Caching)

- **WebSocket overhead is generally light** — Perspective's live binding updates are small, delta-style payloads, so the steady-state bandwidth for an idle-ish dashboard is modest (KBs/minute range), which usually tolerates cellular/LTE fine. The bigger bandwidth costs are at *load time* (initial bundle download) and on *view navigation* (each new View's component tree and any embedded images).
- **Initial load size**: the compiled Perspective project's JS bundle, fonts, and any custom fonts/icons all download on first connect. On a first-time cellular connection (no service-worker cache yet), a heavy project can take several seconds to become interactive; this is the moment users most often bail or report "the app won't load" when it's actually still loading. Keep custom font/icon sets trimmed to what's used, and avoid importing whole icon libraries when a handful of icons are needed.
- **Service worker caching (PWA)**: once installed, the service worker caches static assets aggressively, so subsequent loads are fast even on marginal connectivity — reinforcing why PWA install (Section 1) matters operationally, not just cosmetically: it's the difference between a multi-second reload every session and a near-instant one.
- **Polling-heavy views cost more on metered connections**: field technicians on a metered hotspot/cellular plan will notice a dashboard that polls a dozen bindings every second; audit and lengthen polling intervals for any view expected to run primarily over cellular.
- **Reverse proxy / gzip / compression**: ensure whatever sits in front of the Gateway (nginx, IIS ARR, F5) has gzip/br compression enabled for the Perspective bundle — this is a common "forgot to configure" item that doubles/triples load time on cellular for no reason, since Ignition's own web server compresses by default but a naive reverse-proxy passthrough config can inadvertently disable it.
- **Multi-monitor/large dataset table exports**: large table exports (CSV/PDF generation) triggered from a mobile session pull the same dataset size as a desktop session would — on cellular, a technician tapping "export 50,000 rows" can hang the session or blow through a data cap; consider paginating or restricting export scope on mobile-detected sessions (`session.props.device.type`).

## 5. Security on Mobile Devices (Encryption, Auth)

- **HTTPS is not optional for mobile** — beyond general good practice, several mobile-specific browser APIs (camera, geolocation, service workers/PWA install itself) are flatly refused by mobile browsers over plain HTTP. Any mobile-facing Gateway must have a valid TLS certificate (publicly trusted CA, not just an internal self-signed cert dropped into the Gateway's keystore) — self-signed certs work fine for desktop clients used to clicking through a browser warning once, but the camera/geolocation/PWA-install APIs specifically check for a browser-trusted origin and silently fail on a self-signed cert in a way that's confusing to debug because there's no explicit "insecure origin" error surfaced to the end user, just "the scanner button doesn't do anything."
- **Session/idle timeout on shared devices**: shared kiosk tablets need a shorter idle-timeout/auto-logout than a personal BYOD phone — configure Perspective session idle timeout per-project (or per-page logic) rather than relying on one global desktop-tuned timeout, since a shared handheld left logged in as the last operator is a real access-control gap on a factory floor.
- **Identity Provider / SSO on mobile browsers**: if using an external IdP (Okta, Azure AD, Auth0) via Ignition's Identity Provider configuration, test the full OAuth/SAML redirect flow specifically in the target mobile browsers — in-app browsers (e.g., a link opened from Teams/Slack/Outlook's built-in web view rather than the system browser) frequently break OAuth redirect flows or block third-party cookies, producing a login loop that doesn't reproduce in a normal desktop browser test.
- **Biometric/device-level auth is device-OS territory, not Ignition's**: Face ID/fingerprint unlock protects the *device* or, if the client built a native wrapper, potentially gates *launching* the wrapper app — but it does not replace or integrate with Ignition's own authentication; the Perspective login (username/password, SSO, etc.) still happens independently once the app is open. Don't let a client assume "the phone has Face ID" means Ignition's login is biometric-protected.
- **MDM app/URL allowlisting reduces attack surface**: pairing kiosk mode (Section 2) with URL allowlisting prevents a shared device from being used to browse to arbitrary sites while also authenticated into the Gateway in another tab — a genuine cross-contamination risk on shared handhelds.
- **Local data at rest**: anything cached via localStorage/service-worker (Section 5 of the companion doc — offline drafts, cached last-known values) is stored unencrypted in the browser's app data on the device; for genuinely sensitive data, don't rely on browser local storage as a secure store — a lost/stolen unmanaged BYOD phone can expose that cached data far more easily than the Gateway ever would.

## 6. Troubleshooting Mobile Connectivity

Common mobile-specific connectivity symptoms and their usual root causes, roughly in the order to check them:

1. **"White screen on open" / stuck spinner** — almost always TLS: a self-signed or expired cert, or a captive-portal Wi-Fi intercepting the connection before it reaches the Gateway. Check the cert chain and check whether the device is actually on the intended network (captive portals on guest Wi-Fi are a frequent culprit on-site).
2. **Works on Wi-Fi, fails on cellular** — usually a firewall/VPN split-tunnel issue: the Gateway is only reachable from the corporate network, and the device's cellular connection isn't routed through the VPN/site-to-site tunnel. Confirm whether cellular traffic is expected to be able to reach the Gateway at all before troubleshooting further.
3. **Frequent "reconnecting…" banners on a fixed Wi-Fi tablet** — check for Wi-Fi roaming/AP handoff issues (common on wall-mounted tablets near AP boundaries) and check the reverse proxy/load balancer's WebSocket idle timeout — some proxies default to a 60s idle timeout that's shorter than Perspective's own keep-alive interval, killing the WebSocket even though both device and Gateway are healthy.
4. **Works in browser, fails in installed PWA** — service worker cache holding a stale/broken bundle (Section 1); have the user remove and reinstall the PWA, or clear site data, before assuming a server-side bug.
5. **In-app browser login loops** — see Section 5; identify whether the user opened the link from within another app's embedded browser and have them open in the system browser instead.
6. **Intermittent drop only on one carrier/device model** — worth checking whether that carrier does aggressive TCP connection pooling/proxying (some carrier networks transparently proxy HTTP(S) and mishandle long-lived WebSocket connections) — this is a real, if less common, root cause on some regional carriers.
7. **Camera/geolocation button does nothing, no error shown** — HTTPS/self-signed cert issue (Section 5) or the permission was previously denied at the OS level and needs to be manually re-enabled in the device's per-site browser permission settings, not just re-prompted from Ignition's side.

## 7. Analytics & Usage Monitoring

Ignition doesn't ship a dedicated "mobile analytics" panel, but usage visibility is achievable by combining existing Gateway facilities:

- **Session tracking via Gateway status/scripting**: `system.perspective.getSessionInfo()` and related session-scope scripting can enumerate active sessions and their `device.type`/`userAgent`, which can be logged periodically (via a Gateway Timer script) to a database table to build a simple "sessions by device type over time" report — there's no built-in retention of this beyond what's actively logged.
- **Gateway logs**: the Gateway's web server access logs record every HTTP request including User-Agent, useful for a rougher "what devices are hitting us" picture, though noisier and not Perspective-session-aware.
- **Custom audit logging pattern**: many deployments add explicit audit-log writes (a DB insert on login, on key navigation events, on form submits) tagged with `session.props.device.type`, giving a purpose-built dataset for "how much of our usage is actually mobile" reporting rather than reverse-engineering it from raw web logs.
- **Third-party/browser-side analytics (opt-in territory)**: nothing prevents embedding a standard web analytics snippet (if policy allows sending telemetry to a third party, which many industrial/OT environments explicitly disallow) via a custom component or injected script for page-view/session-duration analytics — evaluate against the client's data governance policy before adding this, since it introduces an external network dependency into what's often an intentionally isolated OT network.

## 8. Offline-First Strategy Implementation

Per the companion doc, Perspective is not offline-first out of the box; implementing an "offline-tolerant" strategy within Ignition's actual capabilities means combining several of the patterns already introduced, applied deliberately:

1. **Define the actual requirement precisely** — "offline" almost always means one of three very different things in practice: (a) tolerate brief connectivity gaps without crashing/blanking (the easy, well-supported case), (b) view last-known cached data while disconnected (moderate effort, localStorage/session-prop caching), or (c) create/edit records while fully disconnected and sync later (hard — effectively requires a separate local-first native app talking to Ignition's REST/webservice endpoints on reconnect, outside Perspective itself). Scope which of these the client actually needs before designing anything; (c) is frequently assumed but rarely truly required once "brief tunnel/elevator dead zone" is disambiguated from "no signal for a full shift."
2. **For (a)**: rely on Perspective's native WebSocket auto-reconnect and design an explicit "reconnecting…" UI state (bind a banner to session connection status) rather than letting components silently go blank — the built-in reconnect logic is solid, the gap is almost always UI communication, not the reconnect mechanism itself.
3. **For (b)**: cache last-known-good values into `session.props` (which survive brief disconnects since they're client-side) with a captured timestamp, and clearly flag staleness in the UI (`"as of HH:MM"`) so operators don't act on silently-stale data.
4. **For (c)**: be explicit with the client that this requires custom native development beyond Perspective — a locally-installed app (React Native, Flutter, or a native shell) with its own local database (SQLite) that syncs to Ignition via `system.webservices`-published endpoints or a REST integration when connectivity returns; budget and scope this as its own project, not a Perspective configuration task.
5. **Test the actual dead zones, not a simulated one** — Wi-Fi/cellular dead zones on a real facility (behind metal shelving, in elevators, in RF-noisy areas near VFDs/welders) behave differently than a laptop's "network throttling" DevTools simulation; validate reconnect behavior walking the actual facility with the actual target devices before sign-off.

## 9. Push Notification Configuration

As covered in the companion doc, native OS-level push is not a Designer-configurable Perspective feature in 8.3. The two realistic paths, with their actual configuration steps:

- **Alarm Notification Pipelines (recommended default)**: configure SMS (via a Twilio/similar SMS notification profile) or email notification profiles under the Gateway's Alarming > Notification section, build a pipeline that routes to on-call operators' phone numbers/emails, and bind alarm shelving/ack actions back into a Perspective mobile view so operators can act on the SMS/email link. This is fully within Ignition's supported configuration surface and is the path to recommend unless the client has a hard requirement for an OS notification banner specifically.
- **Web Push (custom, advanced)**: requires generating VAPID keys, registering the PWA's service worker for a `pushManager.subscribe()` call (custom JS interop), storing the resulting push subscription per user/device (custom DB table), and having Gateway-side scripting call a push service (Firebase Cloud Messaging for both Android and, since Apple added support, iOS Safari 16.4+) with that subscription to actually deliver the OS-level banner. This is genuine custom development, not a Gateway setting — scope it accordingly, and note it only works for installed PWAs, not a plain browser tab.
- **Native wrapper push**: if a custom WebView wrapper already exists (companion doc, Section 10), integrating APNs (iOS) / FCM (Android) push is standard native-app work independent of Ignition, communicating with Ignition only insofar as the wrapper still ultimately loads Perspective content after the user taps the notification.

## 10. Testing on Real Devices vs. Emulators

- **Emulators/simulators are a fast first pass, not sufficient sign-off.** Chrome DevTools' mobile emulation and Xcode/Android Studio simulators are useful for catching gross layout breakage (Section 3 of the companion doc's responsive patterns) quickly during development, but they do not accurately reproduce: real touch latency, real camera/barcode-scanner behavior (simulators fake camera input or skip it entirely), real GPS/geolocation accuracy, real network conditions (cellular vs Wi-Fi vs dead zone), or real battery/thermal throttling behavior under sustained use.
- **Camera, barcode, and geolocation features must be tested on physical hardware** — these are the features most likely to work perfectly in a simulator (which often returns canned/mock permission grants) and then fail silently on a real device due to a permission prompt, HTTPS requirement, or gesture-origin restriction (Sections 5-8 of the companion doc) that the simulator never exercises.
- **Test across the actual fleet's OS/browser versions, not just the latest**: industrial device fleets often run older OS versions than consumer expectation (a Zebra handheld shipped 18 months ago, running an Android version several releases behind current) — verify against the client's actual deployed OS/browser versions, not whatever ships on the developer's personal phone.
- **Test on the actual network the device will use in production** — a feature that works over office Wi-Fi during development can behave differently over the client's actual plant Wi-Fi (often more congested, more RF interference from industrial equipment) or cellular in the actual facility (concrete/metal structures attenuate signal far more than a typical office).
- **Include a mid-range/older device in the test matrix deliberately** — per Section 3, performance problems concentrate on lower-powered hardware; a test matrix of "one current-generation iPhone, one current-generation Samsung flagship" will systematically miss the performance ceiling most of the actual user base experiences on 2-3 year old mid-range devices.
- **Physical walk-test for connectivity-dependent features**: reconnect behavior (Section 8), geofencing (companion doc Section 8), and any dead-zone tolerance work should be validated by physically walking the facility with target devices, not solely simulated via network throttling in a browser dev tool — real RF environments produce failure modes (partial signal, flapping connections) that throttling tools don't reproduce.
