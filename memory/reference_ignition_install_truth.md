The Ignition install is the source of truth, not the KB. Nothing in the Designer is magic; every resource type and component schema ships as a file.

**Install:** `C:\Program Files\Inductive Automation\Ignition` (8.3.7 b2026060908, trial licence, standard edition)

- `data\jar-cache\<moduleId>\` - the jars the gateway actually loads. Read from here, not `data\modules\*.modl`.
- `data\projects\<Project>\<moduleId>\<typeName>\` - project resources, mirroring the `ResourceType(moduleId, typeName)` registry.
- Perspective schemas: `perspective-common-3.3.7.jar` holds `descriptors\*.json`, `schemas\*.json` and seven `*.components.json` files.
- Client bundles: `app-3.3.7.jar` under `mounted\js\`.
- JDK for `javap`: `C:\Program Files\Eclipse Adoptium\jdk-17.0.20.8-hotspot`

**Two KB files were generated from this install on 2026-08-11**, both in `Documents\Projects\ClaudeMem\Ignition-knowledgebase`:

- `04-RESOURCE-MODEL.md` - the full `ResourceType` registry (core `ignition` module, 22 Perspective types, Vision, SQL Bridge, Reporting, alarm pipelines, SFC, WebDev, EventStream), the payload file per type, `resource.json` / `project.json` format, and the `javap` recipe to re-derive it.
- `16-PERSPECTIVE-SCHEMA-TRUTH.md` - schema index, the style precedence chain, the flex prop-to-CSS map, binding and transform schemas, session props, view props, and the full 81-component inventory.

Counts that get quoted wrong: **82 components** total (updated 2026-08-14, was miscounted as 81 on 2026-08-11), not 70 (70 is `ia.components.json` alone, 81 is `perspective-common` alone, 82 adds `ia.reporting.report-viewer` shipped by the Reporting module in its own `reporting-components.components.json`). The KB has **56 component pages**, missing all 5 symbols, all 9 shapes and Nav Links.

**Scripting API verification trick (found 2026-08-14, Reporting module pass):** modules that expose `system.*` functions ship a `*PyWrapper` class (e.g. `ReportScriptingFunctionsPyWrapper` in `reporting-common-7.3.7.jar`) whose bytecode contains the real parameter names as string literals - `javap -p -c` shows them inline (`// String path`, `// String project`, etc.) right where each Jython-callable method builds its `PyObject[]` args. This turns "scripting docs are unverifiable, no shipped stubs" into a real recipe: find the `*PyWrapper` class for a module, `javap` it, read the string constants in order. Used this to catch `71-REPORTING-MODULE.md`'s `system.report.executeReport` example missing its required `project` argument. Worth trying on other modules before assuming a `system.*` namespace can't be checked locally.

**Reporting module (added 2026-08-14):** `ReportResource` (module `com.inductiveautomation.reporting`, type `reports`) has no hand-authorable layout format - the report canvas is a serialized `com.inductiveautomation.rm.shape.RMDocument` (legacy ReportMill/SnapKit), producible only through the Designer's Reporting UI, unlike Perspective's plain-JSON `view.json`. Data sources are a fixed set of 8 classes (SQL prepared/plain, Named Query, Tag History, Tag Calculation, Alarm Journal, Static table, Script) - no such thing as a "Perspective Component" data source. Distribution is 5 concrete schedule-action types (Email, Save File, Print, FTP, Run Script), each cron-scheduled per `ReportSchedule`, not manual `system.net.sendEmail` calls. Full detail in `71-REPORTING-MODULE.md`.

**Reporting module canvas shapes (added 2026-08-14, corrected 2026-08-15):** unlike Perspective, the report canvas has no single schema file - it's a licensed third-party Swing editor (ReportMill, `com.inductiveautomation.rm.*`) with a real Java shape-tree (`RMShape` subclasses), archived to a custom XML dialect via `RMArchiver`. The tag-name registry (`document`, `page`, `table`, `table-group`, `text`, `label`, etc, ~25 live tags) came from `javap -p -c` on `RMArchiver.createClassMap()` - same string-constant trick as the ResourceType registry. Universal shape attrs (`x`,`y`,`width`,`height`,`roll`,`opacity`,...), table attrs (`list-key`, `filter-key`, `columns`) confirmed. **Correction:** the 2026-08-14 note calling `RMXYChart`/`RMPieChart`/`RMTimeseriesChart`/`RMCategoryChart`(=Bar)/`RMRadarChart` "dead weight, not registered" was wrong - they ARE the real, live native Ignition chart components. They're registered dynamically at gateway startup by `ReportingModule` calling `RMArchiver.registerClass(...)` (confirmed via `javap -c` on `ReportingModule.class`), not baked into `RMArchiver`'s static class map, which is why the first pass missed them. Real tag names: `ignition-rm-timeseries-chart`, `ignition-rm-bar-chart`, `ignition-rm-pie-chart`, `ignition-radar-chart`, `ignition-rm-xy-chart` - confirmed against a real Designer-authored reference file the user built by dragging every chart type onto a canvas. `RMGraph`/`<graph>` (the generic ReportMill shape with `type` in `{Bar,BarH,Area,Line,Scatter,Pie}`) is real but is NOT what the Designer's chart palette buttons create - using it produces default/wrong-looking charts. Always use the specific `RM*Chart` class matching the palette button (e.g. `RMTimeseriesChart` for "Timeseries Chart"), never the generic `RMGraph`. Chart color XML attribute join delimiter is genuinely the empty string (verified via constant-pool inspection) - too fragile to hand-write; set colors via the real `setColors(...)` bean setter after parsing instead. Text color is a nested `<color value="#hex"/>` child element, not an attribute (unlike `<fill color="#hex"/>` which IS an attribute) - no consistent rule between shape types, check each one. Also found a second, orthogonal schema layer: runtime annotations (`@ShapeProperty`, `@Preferred`, `@NumberFormatProperty`, etc, package `com.inductiveautomation.reporting.common.api.shape`) on shape setters drive the Designer's property-panel field names. Full writeup: `72-REPORTING-SHAPE-MODEL.md`. A real Java-program write path was built and works: parse hand-written XML via `RMArchiver.readObject(String)`, construct/insert native chart objects via their real bean APIs, wrap in `PageTemplate(RMDocument)`, then `XMLSerializer.serializeAndGZip(ReportResource)` - but always decode-and-diff against a real reference before trusting a new shape type, guessing from bytecode alone produced multiple silent failures (wrong chart type default, dropped text, wrong data-source ID) before this was learned.

**Alarm Notification Pipelines, Transaction Groups, SFCs (added 2026-08-15, alarm pipeline format corrected same day):** three more resource types researched, no live examples existed on this gateway for any of them. **All three turned out to be XML via `ignition.common.xmlserialization.deserialization.XMLDeserializer` - the same fragile framework Reporting uses.** Alarm pipelines were FIRST reported as "plain JSON, safe like Perspective" because the research agent found no Gson usage and concluded JSON by absence - that was wrong and cost a real deploy failure (`SerializationException`/`SAXParseException: Premature end of file` when a hand-written `pipeline.json` was fed to the XML loader). Corrected by tracing the real call: `AlarmPipelineManagerImpl.class` calls `XMLDeserializer.deserialize([B)` directly, confirmed via `javap -c` with an adjacent string constant pinning it to pipeline loading. **Lesson: "no Gson found" only rules out Gson, not this platform's other generic serialization framework - always trace the actual load call, not just search for one library's fingerprint.** All three (alarm pipelines, transaction groups, SFCs) are now being built Designer-guided (real field/block values supplied, user clicks) rather than hand-authored, matching how Reporting eventually had to be handled. Real 10-block alarm pipeline registry (Notification, Delay, Expression, Switch, Jump, PropertySetter, Scriptable/Script, Splitter, EventStream, NoOp) still holds - confirmed via `javap`, full writeup in `41-ALARM-PIPELINE-SCHEMA-TRUTH.md`. "On/Off Ramp", "Add Note", and "Shelve" blocks do not exist. SFC also corrected two invented facts in `28-PLATFORM-TRANSACTIONS-SFCS.md`: `system.sfc.runChart` never existed, the real function is `system.sfc.startChart(chartPath, parameters)`; the chart state enum is a real 15-value 0-indexed enum (`Aborted...RedundantInactive`), not "codes 1-10". No notification profiles (Email/SMS/etc) exist on this gateway - a Notification Block has nowhere to send until one is configured separately.

**Update, same day:** the user built a real pipeline (`AHU_AlarmLog`, Start -> Script block) in Designer, decoded with the same tooling used for Reporting - `data.bin` is the real payload filename (not `pipeline.json`). `PipelineDescriptor` persists as a generic `rawValueMap: Map<String,Object>` of `BasicProperty`/`BasicPropertySet` entries (`com.inductiveautomation.ignition.common.config.*`), not plain bean fields - `startingBlock` is a full embedded object (not a UUID reference) whose `outputId` points at the first real block's `blockId`; canvas position (`ui-location`) and size (`ui-size`) ARE persisted, just generically. Script blocks store body-only, no `def` line - same convention as Perspective event scripts.

**Second update, same day - Inductive Automation's own IADemo reference project** (`.gwbk`/per-project `.zip` exports at `Documents\Projects\Ignition Reference Project\ignition_8_demo_projects.5.0.0\...\Project Backups\IADemo.zip` - inspected read-only, never imported into the gateway) gave real examples for everything still Designer-guided-only: a real `NotificationBlock` pipeline (real key `roster`, not the guessed `onCallRoster`; real `settingsFor_<ProfileName>` per-profile-settings pattern), a real Transaction Group (`GroupConfig`/`ItemConfig`/`MetaPropertyCollection`/`TypedMetaProperty` structure, confirmed the trigger tag is always also a `CONFIGURED_ITEMS` entry with `TARGET_TYPE=NONE`, typeKey `grouptag_sqltref` for tag items), and three real `sfc.xml` charts. **SFC turned out to be the safe case after all** - plain readable XML, no `xmlserialization` framework underneath, grid-based `<link>` connectivity (not ID references, unlike Transaction Groups/Alarm Pipelines which do use UUID references), action-step scripts keep their full `def onStart(chart, step):` line (opposite convention from Alarm Pipeline scripts, which strip it). Full detail in `41-ALARM-PIPELINE-SCHEMA-TRUTH.md` and `28-PLATFORM-TRANSACTIONS-SFCS.md`.
